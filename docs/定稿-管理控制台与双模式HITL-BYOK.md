## 1. 管理控制台与账号体系

### 1.1 命名与入口

- 统一后台名称：**管理控制台**（合并原管理端 + 薄教师能力）。  
- 角色两类：
  - **学生账号**
  - **教师管理员账号**（使用管理控制台；无独立「教师端」产品名）

### 1.2 注册 / 登录（无真实短信）

| 角色 | 字段 | 说明 |
|------|------|------|
| 学生 | 昵称、手机号、**班级码（可选）** | 手机号仅校验 **11 位数字**，不做短信验证 |
| 教师管理员 | 昵称、手机号 | 同上，无班级码 |

登录方式与注册字段对齐（演示态可用手机号+昵称识别账号；具体口令策略实现时定，但**不依赖短信**）。

### 1.3 班级

- 学生：注册/登录时可填班级码加入班级；也可后补绑定。  
- 教师管理员：可 **创建班级 → 生成班级码 → 班级管理**（名单以「持码加入」的学生为准）。  
- **不做**：组卷、判卷、统考闭环、考务 Agent。

### 1.4 管理控制台能力域

| 域 | 能力 |
|----|------|
| 内容 | 题库、回流审核 |
| 班级 | 创建班级、班级码、成员查看、**班级学情—数据分析**（可 Word 导出） |
| 配置 | 账号策略、回流模式等 |
| 可观测（P1） | Agent trace（无对话隐私原文给无关人） |

学生端：个人学情总览、错题、练习、自由问答。  
**竞赛版不做校本大纲裁剪**；§3.1 大纲类需求指学生对话意图梳理，非管理端课程目录裁剪。

## 2. 任务模式、续跑与 Human-in-the-loop

### 2.1 双模式（维持）

| 模式 | 何时 | 行为 |
|------|------|------|
| `react_short` | 单题、单知识点、短输入 | 决策者 + ReAct，自研 ≤3 轮 |
| `plan_execute` | 多题、整卷、文件、大纲长任务等 | TaskList + 分块执行 |

- **单回合 TaskList 上限：5**。  
- **感知优先**：先读懂图片/文件/文字，再判定短 ReAct 或 Plan 长任务。  
- 超限：本回合做前 ≤5 项，说明剩余；每完成一题后可「继续」或「取消任务」。  
- HITL 确认在**对话气泡内**完成（也可回复「确认/取消」），不用模态弹窗。

### 2.2 续跑（都要）

- 口语/指令：「继续」「做后半」等。  
- UI：任务规划模式下的 **「继续未完成任务」** 按钮。  
- 同一 `thread_id` + TaskList 未完成项。

### 2.3 Human-in-the-loop（HITL）——规划模式标配

**凡进入 `plan_execute`，默认插入人工确认闸门**，例如：

1. 路由/解析后生成 TaskList（题块划分、是否绘图、本回合将执行哪些 ≤5 项）。  
2. **展示计划给用户** → 用户确认 / 勾选调整 / 取消。  
3. 确认后再编排执行。  
4. 一块或一轮结束后可再次 HITL：「继续下一块？」或自动停等用户点继续。

短模式 `react_short`：不强制 HITL（避免一题一确认过烦）；用户可随时打断。

## 3. 感知层与文件（定稿）

| 模态 | 支持 | 说明 |
|------|------|------|
| 文字 | ✅ | |
| 图片 | ✅ | |
| docx / pdf / ppt | ✅ | |
| **excel** | ❌ | **不支持上传** |

### 3.1 大纲类需求

- **按学生当下意图**：只要梳理知识点 → 只梳理；只要出题 → 只出题。  
- 也可先梳理，用户下一轮再说出题（自然多轮，不必一次做完）。

### 3.2 七类需求映射（不变精神）

短→`react_short`；多题/卷/长文件→`plan_execute` + HITL；容量超限→拆分 + 续跑；全程护栏，不罢工崩溃。

## 4. BYOK 与 Key 安全模型（定稿原则）

### 4.1 产品规则

- 用户**填写自己的 API Key 之后**：本客户端上的模型调用（含图文与文件相关推理）**一律走用户 Key**。  
- **Key 不上我们的服务器持久化**，管理后台不可见、不可下发他人。  
- 未填 Key：文字/图片可用**平台默认 Key**（服务端代理）；**文件解析/文件任务要求用户先填 Key**（与前议一致并加强为「有 Key 后全走用户 Key」）。

### 4.2 安全设计（推荐实现方向，防「进我们库 / 被他人从我们侧拿走」）

目标：攻击者即使攻破我们的 DB，也拿不到用户 Key；抓我们业务 API 包也看不到明文 Key。

| 措施 | 说明 |
|------|------|
| **浏览器仅存本地** | Key 放在设备侧安全存储（如受同源策略约束的本地加密存储）；**永不写入**我们的 Postgres/日志。 |
| **不进管理端** | 后台无 Key 字段、无展示、无导出。 |
| **调用形态（推荐）** | **客户端直连**用户所选模型供应商（OpenAI 兼容 endpoint），或通过 **同源 BFF 仅做 OPTIONS/文档**，业务求解若需服务端工具（题库/图谱），则：**工具仍走我们后端（无用户 Key）**；**LLM 生成在浏览器侧用用户 Key 完成**，再把「模型输出文本」回传我们后端做匹配/落库（回传的是答案文本，不是 Key）。 |
| **若必须服务端代调 LLM**（不推荐为默认） | 仅允许 **内存态一次性头传递**，禁止落盘；TLS 全程；响应后丢弃。与「不上服务器」字面略冲，故 **默认不采用**。 |
| **防抓包** | 全站 HTTPS；Key 只出现在浏览器→模型商的 TLS 通道，**不出现在浏览器→我们 API 的 JSON 体**。他人抓我们的包看不到 Key；抓用户设备流量仍受系统证书/TLS 保护（无法保证对抗用户本机恶意软件，需在 UI 声明）。 |

### 4.3 架构含义（实现时注意）

```text
有用户 Key 时（示意）：
  感知/文件本地或客户端可解析的部分 → 客户端
  LLM 规划/解题/讲解 → 客户端 + 用户 Key → 模型商
  题库/图谱/学情/落库 → 我们后端（会话 token 鉴权，无 Key）
  HITL / TaskList UI → 前端展示，确认后再触发下一步客户端或后端工具步
```

文件二进制可上传到我们对象存储以便解析服务——若解析也要 LLM，优先 **客户端解析 + 客户端 LLM**；纯规则解析（docx 抽文本）可在服务端做且**不需要 Key**。

## 5. 与运行时分层的合并表述

```text
感知（文/图/docx·pdf·ppt）
  → 语义路由（短 | 长 + 容量）
  → 长任务：HITL 确认 TaskList
  → 决策者回判 + 编排（≤5 原子题/回合）
  → 护栏与可观测
  → 续跑（口令 + 按钮）
```

管理控制台：题库 + 班级码班级 + 班级学情分析；无组卷判卷。
