## 📋 逐层详解

### 第1层：展示层（Presentation Layer）

|属性|说明|
|---|---|
|**定位**|用户直接看到和操作的界面，运行在用户的浏览器中|
|**核心职责**|• 渲染页面（上传区、答案展示区、历史记录）  <br>• 收集用户输入（题目文本、图片文件）  <br>• 发送HTTP请求到后端API  <br>• 接收响应并展示结果（SVG渲染、数学公式）  <br>• 处理用户交互反馈（加载动画、错误提示、评价按钮）|
|**技术选型**|**Vue3**（前端框架）+ **Vite**（构建工具）+ **Element Plus**（UI组件库）|
|**部署方式**|打包为静态文件（HTML/CSS/JS），由Nginx托管|
|**与其他层的关系**|只与**接入层（Nginx）** 通信，不直接接触后端业务|

> **关键理解**：前端代码在**用户自己的设备**上运行，不在服务器上。用户的手机/电脑性能影响前端体验，但不会增加服务器负载。

---

### 第2层：接入层（Gateway Layer）

| 属性          | 说明                                                                                                                                                                          |
| ----------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **定位**      | 系统的“大门”，是所有用户请求到达后端之前的**最后一站**                                                                                                                                              |
| **核心职责**    | • **接收所有用户请求**（HTTPS加密）  <br>• **静态资源服务**：直接返回前端HTML/CSS/JS，不经过业务层  <br>• **反向代理**：将 `/api/*` 请求转发给FastAPI  <br>• **负载均衡**：在多个FastAPI实例间分发请求  <br>• **安全防护**：限流、IP黑白名单、请求日志 |
| **技术选型**    | **Nginx**                                                                                                                                                                   |
| **部署方式**    | 独立容器或直接安装于服务器，监听80（HTTP）和443（HTTPS）端口                                                                                                                                       |
| **与其他层的关系** | • 对**展示层**：提供前端静态资源和API入口  <br>• 对**业务层**：转发API请求，是FastAPI的“保护伞”                                                                                                            |

> **关键理解**：Nginx**不执行业务代码**，只做“分发”和“保护”。FastAPI被隐藏在Nginx后面，外部无法直接访问，大大提升了安全性。

---

### 第3层：业务层（Business Logic Layer）

这是整个系统最核心、最复杂的部分，我们再把它细分为三个子层：

text

┌─────────────────────────────────────────────────────────────────────────┐
│                          【第3层：业务层】                             │
├─────────────────────────────────────────────────────────────────────────┤
│  ┌─────────────────────────────────────────────────────────────────┐  │
│  │  子层1：API接口层                                               │  │
│  │  • 定义路由（/api/analyze, /api/task/status, /api/feedback）   │  │
│  │  • 数据校验（Pydantic验证请求格式）                             │  │
│  │  • 用户认证（JWT Token验证）                                   │  │
│  │  • 依赖注入（数据库会话、缓存连接）                             │  │
│  └─────────────────────────────────────────────────────────────────┘  │
│                                    │                                   │
│  ┌─────────────────────────────────────────────────────────────────┐  │
│  │  子层2：AI Agent层（核心大脑）                                  │  │
│  │  • 意图识别：理解用户想要“画图”还是“查概念”                     │  │
│  │  • 任务规划：决定调用哪个绘图工具，生成什么DSL                   │  │
│  │  • 工具调用：执行SchemaTex/WaveDrom/py-kmap/pinout/FSM Engine   │  │
│  │  • 结果整合：将生成的SVG和文字解析组合成最终答案                 │  │
│  └─────────────────────────────────────────────────────────────────┘  │
│                                    │                                   │
│  ┌─────────────────────────────────────────────────────────────────┐  │
│  │  子层3：绘图工具层（执行的双手）                                │  │
│  │  • SchemaTex引擎：输入DSL → 输出电路图/状态图/框图SVG           │  │
│  │  • WaveDrom引擎：输入WaveJSON → 输出时序图SVG                  │  │
│  │  • py-kmap：输入逻辑表达式 → 输出卡诺图SVG                     │  │
│  │  • pinout（Python库）：输入引脚定义 → 输出引脚图SVG            │  │
│  │  • FSM Engine：输入状态定义 → 输出状态转换图数据               │  │
│  └─────────────────────────────────────────────────────────────────┘  │
└─────────────────────────────────────────────────────────────────────────┘

| 属性          | 说明                                                                                                     |
| ----------- | ------------------------------------------------------------------------------------------------------ |
| **定位**      | 系统的“大脑”和“双手”，负责所有业务逻辑和AI处理                                                                             |
| **核心职责**    | 见上方的子层拆分                                                                                               |
| **技术选型**    | **FastAPI**（Web框架）+ **Uvicorn**（ASGI服务器）+ **LangGraph**（Agent编排框架）                                     |
| **部署方式**    | Docker容器化，可水平扩展多个实例                                                                                    |
| **与其他层的关系** | • 从**接入层**接收转发的API请求  <br>• 向**数据层**读写数据（PostgreSQL/Redis）  <br>• 调用**外部服务**（大模型API、绘图工具的subprocess调用） |

> **关键理解**：业务层是被Nginx“保护”起来的，所有请求必须经过Nginx才能到达这里。这种隔离让业务层可以专注处理逻辑，不用关心安全、加密、静态资源等“杂务”。

---

### 第4层：数据层（Data Layer）

数据层分为两个独立的存储系统，各司其职：

|属性|**关系型数据库**|**缓存数据库**|
|---|---|---|
|**定位**|“档案馆”——永久存储所有结构化数据|“便利贴”——临时存储高频访问的热点数据|
|**存储内容**|• 用户账号信息（用户名、加密密码、邮箱）  <br>• 题目记录（题目文本、上传时间、所属用户）  <br>• 生成结果（SVG代码、图表类型、关联题目）  <br>• 用户反馈（评价、反馈文字）|• 热门题目的答案缓存（Key: 题目哈希, Value: SVG）  <br>• 用户登录Session（Token → 用户信息）  <br>• 限流计数器（IP → 请求次数）  <br>• 异步任务队列（Celery/RQ的任务状态）|
|**技术选型**|**PostgreSQL**（推荐）或 MySQL + **SQLAlchemy**（ORM）+ **Alembic**（迁移管理）|**Redis**|
|**部署方式**|独立容器，持久化存储卷（数据不会因容器重启丢失）|独立容器，可配置持久化（RDB/AOF）|
|**与其他层的关系**|**业务层**通过SQLAlchemy读写；缓存层通过Redis客户端读写|**业务层**通过Redis客户端读写；**接入层**可能在限流场景中读取|

> **关键理解**：PostgreSQL存“永久数据”，Redis存“临时加速数据”。两者都是业务层的“数据来源”，但Redis的数据可以丢失（重建），PostgreSQL的数据绝对不能丢。

## 💎 一句话总结每层

|层级|一句话总结|
|---|---|
|**展示层（Vue3）**|用户看到和操作的界面，运行在用户浏览器里|
|**接入层（Nginx）**|系统的“大门保安”，负责接客、分发、保护|
|**业务层（FastAPI+LangGraph）**|系统的“大脑+双手”，负责思考（AI）和执行（绘图）|
|**数据层（PostgreSQL+Redis）**|系统的“档案馆+便利贴”，负责永久记忆和临时加速|

---

这个四层架构是业界标准的Web应用分层模式，每一层都有明确的职责边界，互不干扰。这样的设计让你可以**独立扩展每一层**（比如业务层压力大就加FastAPI实例，数据层慢了就升级Redis集群），而不会影响其他层。
